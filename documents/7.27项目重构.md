# 项目重构说明文档 - 2026年7月27日

## 一、重构概述

本项目从原始结构重构为更清晰的模块化架构，分离后端（backend/）和前端（frontend/）代码，增强代码组织性和团队协作效率。

### 重构目标
- 按业务模块纵向分片，支持三人团队各自负责独立模块
- 明确的目录结构，便于新成员快速上手
- 支持独立的后端 Maven 项目和前端 Node.js 项目
- 为未来的扩展和维护预留充足空间

**改进建议：**

### 关键文件深度分析

#### 1. **TransactionService.java** - 系统入口
```
功能：
- createTransaction() - 接收交易请求，保存到DB，触发规则引擎
- getAllTransactions() - 查询所有交易
- getTransactionById() - 查询单笔交易
- getTransactionsByAccount() - 按账户查询

架构意义：
- 这是整个系统的触发点
- 每笔交易保存后，都会同步调用 RuleEngineService.evaluate()
- 是"交易→规则→告警"完整链路的第一步
```

#### 2. **RuleEngineService.java** - 规则引擎核心
```
功能：
- evaluate() - 对一笔交易评估所有启用规则
- evaluateAmountThreshold() - 金额阈值规则
- evaluateVelocity() - 交易速度规则
- evaluateNewPayee() - 新收款人规则
- evaluateDailyLimit() - 每日限额规则

架构意义：
- 决定是否生成告警的核心逻辑
- 每个规则类型有独立的评估方法
- 触发规则时创建 Alert 记录
- 将来可以拆分为策略模式，便于扩展

现有问题：
- 四种规则评估逻辑混在一个类中，不符合单一职责原则
- 缺乏统一的规则接口，难以支持新规则快速集成
```

#### 3. **AlertService.java** - 告警生命周期管理
```
功能：
- 状态转换方法：acknowledge(), startInvestigating(), close(), dismiss()
- 状态转换验证：确保只有合法的状态过渡
- 历史记录：每次状态变化都记录到 AlertStatusHistory 表

告警生命周期状态机：
  OPEN (初始状态)
    ↓
  ACKNOWLEDGED (已确认)
    ↓
  INVESTIGATING (调查中) 或 DISMISSED (已驳回)
    ↓
  CLOSED (已关闭)

架构意义：
- 确保告警状态转换的业务规则一致性
- 完整维护审计历史
- 成员C负责的模块核心逻辑
```

#### 4. **MonitoringRule.java** - 规则数据模型
```
字段：
- ruleName - 规则名称
- ruleType - 规则类型（AMOUNT_THRESHOLD/VELOCITY/NEW_PAYEE/DAILY_LIMIT）
- severity - 严重程度（HIGH/MEDIUM/LOW）
- isActive - 是否启用
- thresholdValue - 阈值
- timeWindowMinutes - 时间窗口（分钟）
- maxCount - 最大交易次数

说明：
- 存储到数据库供引擎查询
- 支持动态启用/禁用
- 参数灵活，支持多种规则类型
```

## 五、跨模块依赖关系

### 依赖流转图
```
TransactionController
    ↓
TransactionService
    ↓
TransactionRepository (数据库)
    ↓
RuleEngineService (规则评估)
    ↓
MonitoringRuleRepository (获取启用规则)
    ↓
AlertRepository (创建告警)
    ↓
AlertService (告警管理)
    ↓
AlertController (展示和操作)

DashboardController
    ↓
DashboardService (聚合统计)
    ↓
AlertRepository + MonitoringRuleRepository (查询数据)
```

### 重要的交互点

1. **Transaction → RuleEngine**
   - 由 `TransactionService.createTransaction()` 主动调用 `RuleEngineService.evaluate()`
   - 是同步的，交易保存返回前就完成规则评估

2. **RuleEngine → Alert**
   - `RuleEngineService` 直接调用 `AlertRepository.save()` 创建告警
   - 不经过 `AlertService`（后者主要处理生命周期）

3. **Alert → AlertStatusHistory**
   - `AlertService` 中的每个状态转换方法都会创建对应的历史记录
   - 通过 `AlertStatusHistoryRepository.save()` 实现审计

4. **Dashboard → 各数据源**
   - 从 `AlertRepository`、`MonitoringRuleRepository`、`TransactionRepository` 查询统计数据
   - 不会修改数据，仅用于展示

## 六、数据库表结构预期

基于现有代码推断的表结构：

```sql
-- 交易表
CREATE TABLE transaction (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    account_id VARCHAR(50) NOT NULL,
    payee_id VARCHAR(50) NOT NULL,
    amount DECIMAL(19,2) NOT NULL,
    currency VARCHAR(3) DEFAULT 'USD',
    transaction_type VARCHAR(20), -- DEBIT or CREDIT
    description TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_account_id (account_id),
    INDEX idx_created_at (created_at),
    INDEX idx_account_created (account_id, created_at)
);

-- 规则表
CREATE TABLE monitoring_rule (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    rule_name VARCHAR(100) NOT NULL,
    rule_type VARCHAR(50), -- AMOUNT_THRESHOLD, VELOCITY, NEW_PAYEE, DAILY_LIMIT
    severity VARCHAR(20), -- HIGH, MEDIUM, LOW
    is_active BOOLEAN DEFAULT TRUE,
    threshold_value DECIMAL(19,2),
    time_window_minutes INT,
    max_count INT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 告警表
CREATE TABLE alert (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    rule_id BIGINT NOT NULL,
    transaction_id BIGINT NOT NULL,
    account_id VARCHAR(50) NOT NULL,
    severity VARCHAR(20), -- HIGH, MEDIUM, LOW
    status VARCHAR(50), -- OPEN, ACKNOWLEDGED, INVESTIGATING, CLOSED, DISMISSED
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (rule_id) REFERENCES monitoring_rule(id),
    FOREIGN KEY (transaction_id) REFERENCES transaction(id),
    INDEX idx_status (status),
    INDEX idx_account_id (account_id)
);

-- 告警状态历史表
CREATE TABLE alert_status_history (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    alert_id BIGINT NOT NULL,
    old_status VARCHAR(50),
    new_status VARCHAR(50),
    notes TEXT,
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (alert_id) REFERENCES alert(id),
    INDEX idx_alert_id (alert_id)
);
```

## 十一、常见问题解答

### Q1: 为什么 `model` 改为 `entity`？
**A:** 在 DDD（领域驱动设计）中，`entity` 通常指数据库映射的实体类，而 `model` 较为宽泛。使用 `entity` 更语义明确。

### Q2: 为什么要分离 `dto` 和 `entity`？
**A:** 避免用户看到内部数据结构，提高 API 稳定性。DTOs 专门用于序列化和反序列化。

### Q3: `RuleEngineService` 为什么要重构？
**A:** 当前实现将所有规则评估逻辑混在一起，违反单一职责原则，难以扩展。策略模式可以让每个规则独立，便于维护和测试。

### Q4: 前端代码为什么暂时不实施？
**A:** 根据用户要求，仅建立目录结构，不创建具体的 React 文件。前端实施等待团队的具体计划。

### Q5: 现有项目中的资源文件（schema.sql等）去哪里？
**A:** 复制到 `backend/src/main/resources/`，保持原内容不变。
