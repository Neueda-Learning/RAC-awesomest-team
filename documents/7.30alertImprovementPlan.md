# Alert Improvement Plan (2026-07-30)

## Scope and Constraints
- Single operator/admin mode only.
- No authentication, authorization, or user identity features.
- Prioritize backend query performance and API contracts before UI enhancements.

## Delivery Rules
- Develop in small sub-steps; each sub-step must include code + unit tests + docs update.
- After each sub-step is completed, update this file with: `Status`, `Date`, `What changed`, `API/DB impact`, `Test result`.
- Keep backward compatibility where possible; if a breaking change is needed, document migration notes first.

---

## Priority Roadmap (by dependency and impact)

## Phase 1 - P0: Query Performance + Pagination/Detail APIs + Status Enum
Goal: make alert list queries scalable and standardize lifecycle field typing.

### 1.1 AlertStatus enum (highest priority)
- Replace raw status strings with `AlertStatus` enum in entity/service/controller.
- Keep lifecycle validation rules unchanged:
  - `OPEN -> ACKNOWLEDGED -> INVESTIGATING -> CLOSED`
  - `ACKNOWLEDGED/INVESTIGATING -> DISMISSED`
- Add request/response conversion and invalid-status error handling.

Acceptance:
- Invalid status values are rejected with clear 4xx errors.
- Existing lifecycle unit tests pass.

### 1.2 Backend paginated advanced query API
- Add unified query endpoint (server-side filtering + sorting + paging), example:
  - `GET /alerts/query?page=&size=&status=&severity=&accountId=&ruleId=&from=&to=&sort=`
- Move advanced-search logic from frontend local filtering to backend query.
- Define safe defaults (e.g., `page=0`, `size=20`, max size cap).

Acceptance:
- Large datasets no longer require full-list fetch on the frontend.
- Multi-condition query returns correct subsets and total count.

### 1.3 Alert list vs detail endpoint split
- Keep list payload lightweight for performance.
- Add/confirm detail endpoint for row expansion:
  - `GET /alerts/{id}` returns full alert details.
  - `GET /alerts/{id}/history` returns status timeline.

Acceptance:
- List API response is smaller and faster.
- Row expansion can fetch complete details on demand.

### 1.4 DB indexes for P0 queries
- Add/confirm indexes used by filtering/sorting:
  - `(status, created_at)`
  - `(severity, created_at)`
  - `(account_id, created_at)`
  - optional `(rule_id, created_at)` if query volume needs it.

Acceptance:
- Query latency improves on realistic dataset size.

## Phase 2 - Deduplication + SLA
Goal: reduce alert noise and make handling timeliness measurable.

### 2.1 Alert dedup policy and implementation
- Dedup key baseline: `ruleId + accountId + status(in OPEN/ACKNOWLEDGED/INVESTIGATING) + time window`.
- If hit dedup window, append/merge instead of creating a new OPEN alert.
- Keep clear history/audit note for merged events.

Acceptance:
- Burst transactions do not create excessive duplicate alerts.
- Dedup decisions are traceable.

### 2.2 SLA fields and calculations
- Add SLA-related fields (recommended):
  - `ack_at`, `resolved_at`, `ack_due_at`, `resolve_due_at`, `sla_breached`
- Compute SLA state on transitions and expose in APIs.

Acceptance:
- SLA status can be queried per alert.
- Closed/dismissed alerts have consistent resolution timestamps.

### 2.3 SLA query support
- Add SLA filters/metrics API support (e.g., breached-only view).

Acceptance:
- Can list SLA-breached alerts and verify by tests.

---

## Phase 3 - Dashboard Metrics (Avg Resolution Time + Recent Trend)
Goal: provide actionable operations insight from backend-calculated metrics.

### 3.1 Average handling/resolution time API
- Add metric endpoint for average processing time (from open to closed/dismissed).
- Support date range and optional severity filters.

Acceptance:
- Dashboard displays backend-calculated average duration.

### 3.2 Recent alert trend API
- Add trend endpoint with server-side time buckets (7d/30d; bucket by day).
- Return stable UTC-aligned buckets for chart consistency.

Acceptance:
- Trend chart displays correct counts per bucket including zero-value buckets.

### 3.3 Frontend integration
- Bind dashboard cards/charts to new metric APIs (no full raw data loading for charts).

Acceptance:
- Dashboard loads quickly and charts match API values.

---

## Phase 4 - Bulk Operations + Export
Goal: improve operator efficiency for daily alert operations.

### 4.1 Bulk status actions
- Add bulk transition endpoint:
  - `POST /alerts/bulk/status` (ids + action + notes)
- Return per-item success/failure result for partial success handling.

Acceptance:
- Batch acknowledge/dismiss/close works with clear per-record feedback.

### 4.2 Export with filters
- Add export endpoint:
  - `GET /alerts/export?...&format=csv`
- Reuse same filter params as query API; enforce max export limits.

Acceptance:
- Filtered export is reproducible and consistent with list results.

### 4.3 Frontend batch UX
- Add checkbox selection, select-all, bulk action toolbar, and export action.

Acceptance:
- Admin can complete high-volume operations with fewer clicks.

### 4.4 High-severity email notification
- Add notification flow for `HIGH` severity alerts (single admin mailbox).
- Trigger email on alert creation and keep a minimal delivery log for retries/failures.
- Add config keys for SMTP sender/recipient and enable/disable switch per environment.

Acceptance:
- New `HIGH` alerts send email successfully in configured environments.
- Failures are logged and do not block alert creation.
